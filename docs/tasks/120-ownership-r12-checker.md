## Questions  (agent-maintained; see MANAGER.md 8b)
- Q1 (non-blocking for 120, blocking for live operation; for 008b-3b / the manager). `ci_gate.read_identity` validates the PR author's login against `NAME` (`[A-Za-z0-9](-?[A-Za-z0-9]){0,38}`), and the `login=` output line is validated by the same pattern. GitHub reports a bot author's login as `<app>[bot]` (for example `worldofmodcraft-pipeline[bot]`, the very name `ownership.md` R12 gives). Such a PR would therefore be `Undecided` (exit 2, "malformed number, user id, user login or sha") before any checker runs, so the pipeline's write-back could never reach R12. Not changed here: the login is unrelated to the authorisation (R12 matches the id), loosening an input validator that feeds comment and output lines is a security decision, and the task's file scope and criteria do not cover it. Unverified assumption: that GitHub reports the `[bot]` suffix in `pulls.user.login` for an App installation PR (the contract itself marks the id as unverified until the 008b-2 dry run). My tests use the login `pipeline-bot` for that reason.
- Q2 (non-blocking). Criterion 2 lists "the pipeline identity changing an already-published element (not a T1)" among rejections that carry `R12`. Contract R12 only names PRs that contain a T1 or T3 mutation; a published-element edit is not one, so this implementation rejects it by `R3` plus the residual `fail-closed` rule (tested: `['R3', 'fail-closed']`), and tags `R12` only when the same PR also carries a T1 (also tested). Followed the contract text; if Ludwig wants `R12` on every pipeline-authored rejection, that is a contract change.
- Q3 (non-blocking). 118-verify.sh C10.10 diffs the working tree against e213cbc and allows only 118's files, so on the combined head it necessarily fails by naming 120's files. `120-verify.sh` therefore tolerates exactly that one line, and only if every file it names is in 120's declared scope (with a control that a second failing check is not tolerated). 118-verify.sh itself was not edited (closed). The manager's combined-head re-run of 118-verify.sh will show that one FAIL.
- Q4 (note). Residual `fail-closed` kept: R12 replaced the fail-closed tag for T1/T3 only. Truncation, edits of published/removed/pending elements that are not a T1/T2/T3 keep the `fail-closed` tag in the ownership checker (as the 007b tests `test_b6_truncation...`, `test_b1_deleting_the_file...` and the mutations `b6-truncation-ignored`, `b4-skip-fail-closed` require, byte-for-byte). A file that holds a T1/T3 hit gets only the `R12` finding.
