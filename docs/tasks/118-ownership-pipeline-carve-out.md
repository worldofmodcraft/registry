## Objective
`contracts/ownership.md` declares a new verdict rule **`R12`** and a new checker rule **`I9`**: a PR whose whole change is exactly one T1 (`pending -> published`) or exactly one T3 (`pending -> rejected`) element in exactly one `entry.json` is authorised only when its author is the pipeline identity, and that authorisation lifts `R3` and `R7` (only those) for that PR. Every other PR that contains a T1 or T3 mutation is rejected by `R12`, whoever opened it. `append-only.rules.md`'s two forward references to "the carve-out" now name `R12`. The closed scripts that pin the edited text are re-pinned, visibly, and nothing else in them changes.

## Decisions (manager ★ under ADR-0125, 2026-11-26; logged in the mission log)
- **A★ a new rule `R12`**, not an extension of `R11`. B: widen `R11`. Reason: different identity, different diff shape, and `R11` carries Ludwig's merge gate (I8, MANAGER.md §7).
- **Identity:** `(provider: "github", id: 342916936)`, the user id of `worldofmodcraft-pipeline[bot]`, read from the public API on 2026-11-07 (008b-3a log, umbrella F4). **Not** the App id `5327993`; the contract names both numbers and says which is which. Matched on `pulls.user.id` and provider (`I1`, `I6`), never on the login or `GITHUB_ACTOR*`.
- **Where a checker reads it:** `config/pipeline-identity.json` at the PR's **merge-base** revision (as `I4`), shape `{"schema_version": "1.0.0", "pipeline_identity": null | {"provider": "github", "id": <int>}}`, read by the same rules as `read_r11` in `tools/registry/ci_gate.py:190-205`: absent file = unconfigured, `R12` authorises nobody; a symlink, a non-regular file, malformed JSON, a wrong key set, a wrong `schema_version`, a provider other than `"github"`, or an id that is not `type(id) is int and id > 0` (a string `"342916936"` or `true` never matches) = **no verdict** (the checker stops, as `Undecided` does today). This task does not create the file: the 008b-3a fix round creates it with `null`, 008b-3b sets the id.
- **Exactly one element.** A★ exactly one T1 or one T3 per PR (008b-3a criterion 5); B any number. Reason: one build, one write-back; a multiple or mixed PR is the splice attack task 057 recorded.
- **Detection is broad, authorisation is narrow** (round 1, finding 4). A PR **contains a T1/T3 mutation** iff some `entry.json` it changes has an element whose `status` goes `pending -> published` or `pending -> rejected`, **or** a newly added element whose `status` is `published` or `rejected`, whatever else is wrong with that file or PR; if that cannot be evaluated (e.g. the file does not parse, or has a duplicate key), the PR is rejected by `R12` (fail closed, ADR-0121). `R12` **authorises** only when, in addition, that element is classified by `append-only.rules.md` as a T1 or a T3, and the parsed `new` `entry.json` equals the parsed `old` except for that one element's transition (no top-level key added or changed, no other element changed, `id` and `owner` untouched; 008b-3a's F3), and the PR touches no other path. Byte-only differences that leave the parsed object equal (whitespace, key order) are not a change for `R12`'s purposes; they remain the append-only and schema layers' business.
- **CI is red between the contract and the checker, so they merge together** (round 1, finding 2). `tests/registry/test_ownership_mutations.py` asserts exactly 11 R and 8 I rules and a test pair per rule, so a contract adding `R12`/`I9` turns the registry gate red until the checker implements them. Options: A★ this branch is reviewed on its own, then the 008b-3a fix round is built on top of it (a new branch from this one's head, carrying 008b-3a's work), and one PR merges both after one whole sweep; B merge the contract alone with a red gate (stop-the-line, ADR-0099); C put the test-count edit here (a test changed without the code it tests). **This task does not open a PR and does not merge.**
- **Protection of `config/pipeline-identity.json`** (round 1, finding 5): `ownership.md` governs paths under `mods/` only (R1), so the file is protected by the merge gate, as `r11-identity.json` is today: every registry merge is the manager's under MANAGER.md §7, and no CODEOWNERS or branch-protection rule exists. The contract says this plainly in the attack answer. Booked, not done here: a question for a later task on CODEOWNERS / branch protection for `config/` (it would be a remote change, MANAGER.md §3.9).
